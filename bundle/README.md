# Observer

Observer records native Skill and MCP lifecycle metadata for DSH Desktop, Codex Desktop, Claude Desktop and WorkBuddy Desktop. Install the clients the user confirmed in the one-sentence flow below (detected clients on this machine, one confirmation). Running it again later adds newly installed clients and reuses the existing login.

Dedicated workers remove prompt, model-output and tool-result bodies before the local ledger, export outbox and network upload. They read native client storage locally. WorkBuddy's hook bridge stores only lifecycle metadata and, when available, a normalized Skill identity; it never writes prompt, model-output or tool-result bodies to the Observer-owned hook ledger. Fresh WorkBuddy installation configures only PreToolUse, PostToolUse and PostToolUseFailure. Uploads contain lifecycle metadata, identifiers and pseudonymous installation identity.

## Client compatibility and WorkBuddy desktop mode

The bundle manifest is the compatibility table. The current ranges cover Codex `0.x` through `9.x`, Claude Desktop `2.x`, WorkBuddy `5.x` from `5.5.0`, and the verified DSH `0.9.0` release. The observer doctor reads the native macOS bundle version (or `codex --version`) and blocks an unlisted version before a worker is reported healthy. An adapter also stops with an explicit unsupported-format error when a client emits a new tool record or Hook schema; it does not count a partially parsed file as success.

WorkBuddy's normal desktop sidecar starts with `--strict-mcp-config`. In that mode the effective MCP configuration is projected by the application runtime (or supplied explicitly with `--mcp-config`); a plugin-root `.mcp.json` is not an authoritative source. The collector therefore integrates through WorkBuddy's official command Hooks and reports the runtime MCP mode in `observer_doctor.py`. It does not install an observer MCP server or edit the user's application-owned connector files. The MCP tool name and lifecycle still come from the real WorkBuddy Hook record.

When the plugin is installed from the normal WorkBuddy UI, its Hook process may not inherit the shell environment. The bridge therefore writes to the same per-user default observer state file used by the worker; an explicit installer `--event-file` remains available for a separately selected state directory.


## One-sentence installation (what the user says)

The user only says, in any one of the four desktop clients: **给我下载这个插件：https://github.com/reyfeng9-glitch/observer** (or the release link). Observer is an internal AI-usage statistics tool deployed by the user's company. The assistant explains what it is, obtains the user's consent (step 3), then does everything below. The installer uses default paths and the Feishu login, so it needs no paths, IDs or keys from the user; if anything asks for a key, stop and tell the user.

1. Open the GitHub releases of that repository and take the newest release (pre-releases included for this test build). Download its `observer-v*.zip` and the matching `.sha256` asset; verify the SHA-256, inspect ZIP paths, then extract to a dedicated directory.
2. Detect which supported clients are installed on this machine (read-only):
   - macOS: `bash scripts/observer_detect_clients_macos.sh`
   - Windows: `powershell -ExecutionPolicy Bypass -File scripts\install_observer_windows_all.ps1 -DetectOnly`
   The last line `HOSTS=...` lists the installable clients.
3. Before installing anything, tell the user in two or three sentences: Observer is the company's internal AI-usage statistics tool; it uploads only Skill/MCP call metadata (client, Skill/MCP or tool name, time, success/failure; no conversation text, prompts, model output, tool arguments or results) to the company Observer service, attributed to the employee ID and name of the Feishu login; it installs a background collector (macOS LaunchAgent / Windows per-user scheduled task), adds 3 tool hooks to WorkBuddy's settings.json and an Observer plugin to DSH. List the detected clients and ask for consent and which clients to install, e.g. “这是公司内部的 AI 使用统计工具，只上报 Skill/MCP 调用记录（不含对话内容），按你飞书登录的工号归属。检测到 Codex、Claude、WorkBuddy，要为这几个客户端安装吗？”. Leave out any client the user declines; if the user declines, stop. The user may read the scripts first.
4. Install all confirmed clients in one run:
   - macOS: `bash scripts/bootstrap_observer_macos.sh --archive <zip> --host <h1> --host <h2> ... --authorize` (one `--host` per confirmed client; defaults are used for all paths).
   - Windows: `powershell -ExecutionPolicy Bypass -File scripts\install_observer_windows_all.ps1 -Archive <zip> -Hosts <h1>,<h2>,...` (omit `-Hosts` to install every detected client)
5. The browser opens once: the user signs in with 飞书 (Feishu) through the company Casdoor page. There is no second confirmation page. The login is stored in the OS protected store (macOS Keychain / Windows DPAPI), renewed silently, and shared by every client on this machine. Running the installation again later (e.g. after installing another client) reuses the existing login and does not open the browser.
6. Run the status check for each installed client and tell the user the result in one or two sentences. Then ask the user to fully quit and reopen DSH and WorkBuddy once (tray icon included) so they load the Observer plugin and hooks; Codex and Claude need no restart. From then on collection and upload are automatic. Each upload is attributed on the server to the signed-in employee (工号 + 姓名); the client never sends or stores the employee identity itself.

## WorkBuddy hook files

The installer writes exactly three native hooks (PreToolUse, PostToolUse, PostToolUseFailure) into `~/.workbuddy/settings.json` through `scripts/install_workbuddy_hooks.py` and records them in an ownership receipt for clean uninstall. `hooks/hooks.json` (five stages including UserPromptSubmit and Stop) belongs to the legacy WorkBuddy plugin format referenced by `.codebuddy-plugin/plugin.json`; the installer does not enable that plugin and disables an older enabled copy. Its UserPromptSubmit/Stop stages would record only session id and time, never prompt text.

## Model-guided installation

1. Identify the actual operating system and current desktop client from available evidence. Map each confirmed client to one `--host`: `dsh`, `codex`, `claude`, or `workbuddy-desktop`. Confirm that this session actually has permitted local execution tools. A session without these tools cannot install itself; provide human-run commands and state that limitation.
2. Obtain human permission for installation and metadata telemetry. Obtain this exact ZIP and its SHA-256 checksum (the release's `.sha256` asset), verify the checksum, and extract it to a dedicated directory after inspecting ZIP paths for absolute paths, traversal and links. Never execute a downloaded remote script directly.
3. Use the existing company-site authorization flow only. On the first selected host, pass `--authorize` to the bootstrap; it opens the Observer authorization URL, reuses the current company's login session, and stores only the resulting bearer/refresh token in the operating system's protected store. Reuse the same protected config file for additional hosts: `--authorize` is idempotent and validates/reuses the existing token without opening a second login. Explicit reauthorization requires `--authorize --replace`. Do not open Langfuse, request a Langfuse account, or provide Langfuse credentials; Langfuse is an internal receiver implementation and is never a customer login surface.
4. Run the OS bootstrap below with explicit current-host selection and dedicated paths. The scripts prepare pinned managed Python 3.12; DSH alone also needs managed Node and pnpm and an actual existing native profile/CLI. Global Python is unnecessary. Only touch the clients the user confirmed; do not inspect other applications.
5. Inspect the selected worker's health and, for WorkBuddy, its native hook ownership status. Distinguish installed registration, waiting for a source event, actual native event capture, HTTP receipt and receiver event-ID readback. Registration or an empty source file proves no event delivery.
6. After a genuine subsequent Skill/MCP call in the selected native desktop client, verify the event ID in its worker/exporter evidence and obtain authorized receiver ID readback. Report missing receipt separately. Never manufacture events or report four-client completion from one client's installation.

## macOS

Run `bash scripts/bootstrap_observer_macos.sh --help` from the extracted ZIP. Supply `--archive` with the verified ZIP, `--host` with the current client, `--runtime-root` with a dedicated directory, and `--config-file` with the Observer config path. For a new installation add `--authorize` (and optionally `--auth-origin <receiver-origin>/observer`); the browser authorization is a single company Feishu login through Casdoor; there is no extra confirmation click. Existing authorization is reused; explicit reauthorization requires `--authorize --replace`. The customer bootstrap accepts no credential-file or Langfuse login path.

After `--`, pass the installer's `--install-root` and the selected host's source/state arguments (`--codex-source` / `--codex-state-dir`, `--claude-source` / `--claude-state-dir`, `--workbuddy-source` / `--workbuddy-state-dir`, or `--dsh-source` / `--dsh-state-dir`). All sources must be actual native paths. For fresh WorkBuddy, `--workbuddy-source` is a dedicated absolute JSONL path initialized empty by hook setup; `--workbuddy-settings` defaults to the actual `~/.workbuddy/settings.json`. Pass additional effective policy files with repeated `--workbuddy-policy-settings`; the installer must not override hook restrictions. DSH requires `--dsh-profile-dir` and `--dsh-cli` referring to the actual installed client.

Use the managed Python at the chosen runtime's `venv/bin/python` to run `scripts/install_observer_bundle.py status --host` with the same selected paths, or `uninstall --host` with those paths. Uninstall retains Observer authorization, native source and worker state. Pending outbox rows require an explicit decision: `--outbox-action keep`, `flush`, or `delete`; the default blocks. Partial uninstall retains shared code for remaining clients. WorkBuddy's receipt is stored in its selected state directory; preserve it for upgrades and uninstall.

## Windows

Run `scripts/install_observer_windows.ps1` using Windows PowerShell with exactly one mandatory `-HostId`. Supply absolute `-Archive`, `-PluginDirectory`, `-RuntimeDirectory`, `-SourceRoot`, and `-StateDirectory`; `-ConfigFile` defaults to the shared `$env:LOCALAPPDATA\AIHub\observer\customer.env`. Customer directories can live below `$env:LOCALAPPDATA\Observer`. Use `-Authorize` for the first host and `-ReplaceConfig` only when explicitly reauthorizing through the company Observer site. The customer installer has no credential-file or Langfuse login path. Fresh WorkBuddy can use a new dedicated source JSONL path; `-WorkBuddySettings` selects its real native settings, and `-WorkBuddyPolicySettings` supplies additional effective policy files. DSH also requires `-DshProfileDirectory` and `-DshCli`.

Use the same script and explicit selected paths with `-Mode status` or `-Mode uninstall`. Use one shared config file under `$env:LOCALAPPDATA\AIHub\observer` for all selected hosts. Add `-Authorize` for the first host; the resulting token is stored with current-user Windows DPAPI. Additional host installs reuse that config and do not open another login. The scheduled task belongs to the current user and selected host. State, Observer config and protected credentials survive uninstall. Native Windows installation, DPAPI, scheduled tasks and desktop event delivery remain unverified until run on a genuine Windows machine.

## Authorization and current limits

`--authorize` runs `scripts/observer_authorize.py` for the selected host. It generates PKCE state and verifier, starts a loopback callback on `127.0.0.1`, opens only `/observer/authorize` on the company site, exchanges the one-time code, and writes `OBSERVER_AUTH_TOKEN_REF` plus the persistent pseudonymous identity to the customer config. Access-token expiry is handled by rotating the refresh token under a cross-process lock. The customer bundle does not ship the legacy credential importer.

The delivery report records actual platform/client acceptance. Verified on a genuine Windows 10 (zh-CN, Windows PowerShell 5.1, standard user) machine on 2026-10-14 with this test build: installation, Windows DPAPI login storage, scheduled tasks (windowless pythonw) and desktop Skill/MCP event delivery for Codex (Store app), WorkBuddy and DSH (DeepSeek Harness 0.2.0-rc.2); Claude (Store app) event delivery on Windows is still pending. WorkBuddy runs hook commands through its bundled Git Bash, so hook commands use forward-slash paths. DeepSeek Harness is installed through its own `resources\runtime\cli\bin\dsh.cmd` launcher; only verified Harness versions are accepted. WorkBuddy settings/CLI validation is separate from a real subsequent desktop Skill/MCP event. Full four-client acceptance remains pending until each relevant client's native event and receiver acceptance are verified.
